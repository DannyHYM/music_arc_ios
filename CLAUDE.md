# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

MusicArc Forest — an iOS rehab game for burn-recovery patients (shoulder/axilla stretching). The patient raises their arm above a threshold to "grow" a procedurally-drawn tree; lowers it during rest to "water" it. See `INVENTION_DISCLOSURE.md` for the clinical rationale and `SOUND_EFFECTS.md` for the audio spec (most SFX are still procedural placeholders).

- iOS 18+, Swift 5.9, SwiftUI, portrait only
- **No third-party dependencies.** Everything is Apple first-party (SwiftUI, Vision, AVFoundation, AVAudioEngine, SwiftData, Combine). Do not introduce SPM/Pods/Carthage packages — that's a hard project constraint, see `INVENTION_DISCLOSURE.md` §13.
- All visuals are SwiftUI `Canvas` drawing (no image assets). All sounds are PCM synthesized at runtime in `AudioManager`. The only files under `Resources/` are sound placeholders and asset catalog stubs.

## Build / Run

The Xcode project is generated by **XcodeGen** from `project.yml`. If you change source layout or add files, regenerate:

```sh
xcodegen generate     # rewrites MusicArc.xcodeproj from project.yml
```

Then build/run from Xcode (`MusicArc` scheme, iOS 18 simulator or device). There is **no test target** and no SwiftPM/Makefile — `xcodebuild` works if needed, but the normal workflow is Xcode.

Camera-based pose detection requires a real device. The simulator falls back automatically: `GameConfig.cameraAvailable` returns `false` under `targetEnvironment(simulator)`, and `InputMode.touch` / `.demo` are the usable paths there.

## Architecture

### Navigation
`ContentView` owns a `NavigationStack` driven by the `AppRoute` enum: `home → calibration → game → summary`, plus `history` and `treePreview`. Routes carry their config payloads (`GameConfig`, `CalibrationData`, `GameResult`, `TreeSpecies`), so views are pushed with all the state they need — there is no shared "current session" singleton.

### Game loop — `GameEngine`
`GameEngine` (in `Game/`) is an `@Observable` class that is the single source of truth during a session. It owns:

- A phase state machine: `.countdown → .active → .rest → .complete`, advancing through a pre-generated `[Rep]` array from `RepScheduler`.
- A 30 Hz `Timer` (`tick()`) that reads `currentArmHeight` and updates `treeGrowth`, `treeHealth`, `waterLevel`, and per-rep accumulators.
- A `PoseProvider` subscription that feeds raw arm-height values, which are then normalized through `CalibrationData.normalize(...)` before being used by the loop.

Scoring lives in `ScoreTracker` (growth %, tree health, rest compliance averages). `GameEngine.buildResult()` flattens everything into a `GameResult` for the summary screen, which the user can persist to `GameSession` (SwiftData).

Key invariants when touching the engine:
- `tick()` is the only place game state advances. Audio cues (`AudioManager.shared.playX`) are fired from inside the relevant phase branch — don't add audio from views.
- Pause/resume must adjust `startTime` by the pause duration so `elapsedTime` stays continuous (see `pause()` / `resume()`). New phase logic must not assume monotonic wall-clock time.
- The `restBonusMultiplier` is computed at the **start** of each active phase from the previous rest's `waterLevel` — moving this computation will silently break the rest-incentive mechanic, which is the clinical core of the app.

### Pose input — `PoseProvider` protocol
Three interchangeable providers in `Tracking/`, all publishing a `Double` (0..1) via `armHeightPublisher` (Combine):

- **`PoseDetector`** — `VNDetectHumanBodyPoseRequest` on `AVCaptureSession` frames from `CameraManager`. Tracks shoulder/elbow/wrist of the configured arm (`TrackingArm.left|.right`); also exposes `armPosePublisher` for the on-screen skeleton overlay.
- **`TouchPoseProvider`** — drag-to-set; `GameEngine.touchProvider` is exposed so `GameView` can wire up gestures.
- **`DemoPoseProvider`** — sine-wave automation for screenshots/clinician demos.

When adding new inputs, conform to `PoseProvider` and add a case to `InputMode` + `GameEngine.beginGameplay`. Don't add input branches scattered across views.

### Rendering — `TreeRenderer` protocol
`TreeSpecies` enum maps each species to a `TreeRenderer` (`OakTreeRenderer`, `RoundTreeRenderer`, `BushyTreeRenderer`, `PineTreeRenderer`, `AcaciaTreeRenderer`). All renderers take `(growth: Double, health: Double)` and draw into a SwiftUI `GraphicsContext`. New species = new renderer + new enum case + update `TreeSpecies.renderer`. There are no image assets to add.

### Audio — `AudioManager`
Singleton that synthesizes sine-wave chords with ADSR envelopes into `AVAudioPCMBuffer`s at 44.1 kHz and plays them via `AVAudioPlayerNode`. Countdown uses two iOS system sounds (1104 / 1025) as placeholders. Per `SOUND_EFFECTS.md`, real assets are still TODO — if you add `.m4a` files under `Resources/Sounds/`, prefer extending `AudioManager` rather than playing from views directly so all audio stays mixable with other apps (the session is configured `.playback` + `.mixWithOthers`).

### Persistence — SwiftData
Only one `@Model`: `GameSession`. The container is built in `MusicArcApp.sharedModelContainer` with a **destructive fallback**: if the schema fails to open, the store + `-shm`/`-wal` files are deleted and recreated. This is fine during prototyping but means **migrations are not handled** — if you change `GameSession`, existing user history will be wiped on next launch. Add a real migration before the app ships.

## Conventions worth knowing

- Models are plain `struct` value types (`GameConfig`, `CalibrationData`, `GameResult`, `Rep`) except `GameSession` (SwiftData) and `GameEngine` (observable class). Keep this split — views diff `@State`/`@Observable` reads cleanly because of it.
- `GameConfig` defaults to **8 reps × (4s active + 3s rest)** with a 0.7 sunlight threshold and 0.3 rest threshold. These numbers are clinical defaults — change them in `GameConfig` rather than per-call.
- The `Info.plist` is generated (`GENERATE_INFOPLIST_FILE: YES`); camera usage description and orientation lock live in `project.yml`. Edit there, then `xcodegen generate`.
